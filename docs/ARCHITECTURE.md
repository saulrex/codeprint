# codeprint — архитектурный скоуп

> **Статус на 2026-11-07**: рабочий пайплайн end-to-end. Пять осей
> (blanklines, wrapping, imports, naming + filefeat для стилометра),
> composer с профилями, syntax-gate, audit, similarity, bench.
> 81 тест зелёный. Главные измеренные цифры — в README
> (таблица «Измеренные результаты»).

Карта модулей проекта. README отвечает за «как запустить», этот документ —
за «из чего состоит система и что строить дальше».

Базовый паттерн всей системы: **модуль решает — движок применяет — метрика
проверяет**. Нейронка никогда не пишет код напрямую; она отвечает на узкие
вопросы («сколько пустых строк здесь: 0/1/2»), а применяют решения
детерминированные, проверяемые движки.

## Слой 1 — стилевые оси (модули-трансформеры)

Каждый модуль реализует контракт `Decider`/`Transformer` и подключается
plug-and-play. Нейронный decider и эвристический профиль взаимозаменяемы.

## Уроки второго аудита (naming + syntax-gate, 2026-11-06)

1. **Position staleness**: замены по позициям маски протухают после замены
   другой длины. Правило: собрать ВСЕ совпадения строки, применять справа
   налево. (Порождало мусор вида `neautoDownshiftndent`.)
2. **Порядок осей важен**: naming меняет длины строк → решения wrapping
   расходятся между прогонами. Зафиксировано: imports → naming → wrapping →
   blanklines.
3. **Идемпотентность → сходимость**: naming-гварды зависят от текста после
   других осей; apply(apply(x)) ≠ apply(x) на первом шаге, с 2→3 стабильно.
   Политика: «применять до неподвижной точки».
4. **Стабилизация renamer'а**: имя, чьи слова уже в словаре автора, не
   переименовывается — фиксирует точку сходимости.
5. Токен-аудит с naming: переименования — ожидаемые потери/приходы; известный
   false positive, когда новое имя в lowercase совпадает с существующим
   токеном.

## Модуль 8: `harvest` — сборщик чистого датасета, поставка в .exe

### Зачем отдельная поставка

Сборщик запускается один раз на машине автора, не требует Python-окружения
и не тащит за собой весь проект. Поэтому упаковывается в standalone `.exe`
(PyInstaller, `--onefile`).

### Вход (параметры CLI / интерактивный опрос)

```
harvest.exe --repo https://github.com/<user>/<repo> [--repo ...]
            --author <login | email | id>      # чьи коммиты брать
            --before 2026-11-06                # дедлайн: коммиты ПОСЛЕ не берём
            [--token <github-token>]           # для приватных репо / API-лимитов
            [--out dataset/]
```

`--before` — ключевой параметр: это момент, после которого автор начал
«вливать нейронкой». Всё позже дедлайна в датасет не попадает, чтобы модель
училась на чистом человеческом стиле, а не на смеси с генерацией.

### Что делает

1. Клонирует репозиторий целиком (`--shallow-since` не подходит: он отсекает
   историю **до** даты, а нам нужно ровно наоборот; «shallow-until» в git нет).
2. Отбирает коммиты: `git log --author=<author> --before=<date>`; merge-коммиты
   и коммиты ботов пропускает.
3. Для каждого отобранного снапшота файла извлекает обучающие пары по каждой
   стилевой оси. Для `blanklines`: на каждой границе логических строк —
   признаки контекста + label 0/1/2 (сколько пустых строк поставил автор).
4. Пишет датасет в `--out` (JSONL на ось + `manifest.json`: репо, диапазон
   дат, число примеров, хэш параметров запуска для воспроизводимости).

### Почему такие решения

- **Git-история, а не GitHub API**: API отдаёт файлы, но с историей мы можем
  резать по дате и автору нативно, без квот; токен нужен только для приватных
  репо.
- **Фильтрация по author, а не committer**: коммитером может быть CI/бот.
- **Дедупликация**: одинаковые файлы из соседних коммитов в датасете
  схлопываются по хэшу, иначе модель переобучится на «горячих» файлах.
- Результат `harvest` — это вход для `trainer` (модуль 9).

## Порядок MVP

```
harvest (8) ──> trainer (9) ──> stylometer (10) ──> planner (14)
                                    ▲
imports (2) → wrapping (3) → gate (11) → naming (4) → idioms (5)
```

1. `imports` — вторая ось, разминаем plug-and-play на простом.
2. `harvest` — без него нейронке нечего есть.
3. `trainer` + `stylometer` — парные, проверяют друг друга.
4. `wrapping`, полноценный `gate`, потом `naming`.
5. `structure` и `ts_backend` — хвост, когда ядро докажет себя на Python.

## Stylometer v3 — отрицательный результат (2026-11-06)

Гипотеза: файл-уровневые мульти-осевые признаки (12 статистик: blank_rate,
wrap-rate по бакетам длины, схемы импортов…) различат автора лучше
граничной модели. Реальность: **val accuracy 0.597 — уровень случайного**,
и файл автора скорится НИЖЕ файла коллеги (0.465 vs 0.528).

Причина найдена прямым сравнением признаков по классам: в `myrepo` стоит
prettier (printWidth=80), и поверхностный стиль у всех соавторов одинаковый —
blank_rate 0.377 vs 0.375, wrap_120p 0.815 vs 0.814. Форматтер стирает
личный почерк с поверхностных осей. Граничный стилометр на
внутри-функциональных границах тоже не улучшился (0.611 vs 0.616).

**Вывод для роадмапа:** в репозиториях с автоформаттером атрибуция по
поверхностным осям (blanklines/wrapping/imports) не работает между
соавторами — сигнал живёт глубже: naming (словарь имён), idioms (выбор
конструкций), структура функций. Эти оси становятся приоритетом (модули 4-5).
Поверхностные оси остаются полезными для наложения «внешнего вида»
и против чужих репозиториев (Герганов: 0.283).

## Уроки аудита перед stylometer v3 (2026-11-06)

Прогон `examples/audit.py` (300 файлов myrepo, профиль you):

1. **Критичный баг, пойманный глазами, а не проверками**: wrap_statement
   переносил скобки управляющих конструкций (`if (...)`) — trailing comma там
   syntax error в TS, а в Python `if (a,):` — всегда-истинный кортеж.
   Токен-инвариант это НЕ ловит (токены валидны). Фикс: перенос только
   скобок вызовов. **Урок: для TS нет syntax-gate — нужен tree-sitter parse
   как проверка (связывается с модулем 15).**
2. Токен-инвариант + whitelist trailing comma: 292 tokens_ok + 8 осознанных
   trailing comma (стиль из .prettierrc trailingComma:all). 300/300
   идемпотентно.
3. Вклад осей (из 300 файлов): blanklines 154, imports 40, wrapping 25.
4. Стилометр v2: средний сдвиг +0.0007, но ~30 файлов уходят В МИНУС —
   усреднение по всем границам размывает сигнал и добавляет шум.
   **Для v3: скорить только «решательные» границы (где авторы расходятся)
   и/или взвешивать по уверенности модели.**
5. Профиль обучен на TS; применение к Python — кросс-доменно. Для v3:
   язык как признак или per-language профили.

## Сквозные принципы

- Нейронка решает, движок применяет — никогда наоборот.
- Каждая трансформация проходит `gate` или откатывается.
- Публичные API, сигнатуры, экспортируемые имена — вне зоны досягаемости.
- Профиль автора — данные (`profile_store`), а не захардкоженная логика.
